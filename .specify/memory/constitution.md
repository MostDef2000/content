# Content SDD Constitution

Version: 1.0.0
Status: Active
Ratified: 2026-09-13

Этот constitution настраивает SDD-слой проекта `content`. Канонический
процесс доставки наследует практику воркспейса (sdd-delivery) и упрощён
соразмерно проекту: нет автономного production-контура и standing delegation —
все серверные действия идут через handoff-цикл с явным подтверждением.

## I. Product outcome before implementation
Каждая значимая работа начинается с наблюдаемого результата и защищённых
границ, до деталей реализации.

## II. Спецификации — долговременный продукт
`specs/<feature>/spec.md` фиксирует ЧТО/ЗАЧЕМ. GitHub Issues — канонический
backlog, авторизация и audit-история.

## III. Планы объясняют архитектуру и решения
`plan.md` фиксирует КАК, затронутые контуры, решения и отклонённые
альтернативы, риски и план проверки.

## IV. Задачи ограничены и исполнимы
`tasks.md` фиксирует ограниченные единицы работы и completion gates.
Существенное изменение scope проходит обычную авторизацию заново.

## V. Runtime-реальность питает SDD
Результаты деплоя/приёмки/эксплуатации обновляют активные артефакты фичи.
Исторические Issue/PR не переписываются задним числом.

## VI. Простота
Минимальная работающая архитектура, удовлетворяющая результату и границам.

## VII. Authority
SDD-тексты не выдают авторизацию. Source authorization — полная видимая
область работ, за которой в **следующем** сообщении пользователя следует
точная фраза `commit approved`. Серверные действия — отдельный handoff-цикл
(`SYSADMIN-HANDOFF v1`) с исполнением и подтверждением на стороне агента.

## VIII. Traceability
Значимый PR/коммит-сет ссылается ровно на один feature spec; acceptance
критерии трассируются в задачи и evidence-пути.

## IX. Feature identity
Канонический идентификатор фичи — полное имя каталога `NNN-feature-slug`.
Числовой префикс — только порядок. Дубликаты префиксов запрещены.

## X. Автоматизация без скрытого состояния
Продуктовые решения живут в GitHub-артефактах, а не только в памяти агента/чата.

## XI. Качество доставки
Для связанных значимых работ: NFR-оценка в `spec.md`; risk profile и тест-дизайн
в `plan.md`; acceptance-трассируемость и Definition of Done в `tasks.md`.
Низкорисковая работа может явно помечать `Risk profile: NOT REQUIRED`.

## Standard lifecycle

```text
Issue + видимая область работ
-> commit approved
-> spec / plan / tasks (при значимой работе)
-> реализация + проверки
-> commit/push (в рамках принятой области)
-> деплой через SYSADMIN-HANDOFF (отдельный цикл)
-> runtime-фидбек записывается обратно
```
